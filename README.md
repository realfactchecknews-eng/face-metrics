# FaceRate — AI-оценка лица (looksmaxxing / PSL)

Веб-приложение: пользователь загружает фото, приложение считает геометрию лица
**локально** в браузере, отправляет фото на ИИ и показывает PSL-оценку, разбор по
8 категориям и рекомендации. Есть сравнение двух лиц («Who Moggs?»), аккаунты, оплата
(Telegram Stars / крипта / карта РФ через Lava.top) и отдельный бот техподдержки с
AI-ответами и панелью модератора.

- **Прод:** https://facerate.ru
- **Репо:** `realfactchecknews-eng/face-metrics`, рабочая ветка — **`master`**
  (это важно: есть старая фича-ветка `claude/face-geometry-tool-*` без бота и
  платежей — не путать, весь актуальный код только в `master`)
- **Бэкап:** `realfactchecknews-eng/face-metrics-backup` (приватное зеркало `master`
  на случай, если основной репозиторий/аккаунт пострадает; обновлять вручную по мере
  необходимости — автосинхронизации нет)
- **Бот оплаты:** [@faceratepay_bot](https://t.me/faceratepay_bot)
- **Бот поддержки:** [@FaceRateSupport_bot](https://t.me/FaceRateSupport_bot)
- **Бот медийных партнёров:** [@FaceRateMedia_bot](https://t.me/FaceRateMedia_bot) — самостоятельная статистика по реферальным ссылкам
- **Канал:** @wwwfacerateru

> Развлекательный сервис. Оценка — субъективная эвристика ИИ, не диагноз и не истина.

- **Детекция:** FaceLandmarker (`tasks-vision`, IMAGE mode), 468 точек, локально в браузере,
  файлы библиотеки — свои (`vendor/mediapipe/`), не CDN.
- **ИИ-анализ:** Cloudflare Worker → OpenRouter, модель **`x-ai/grok-4.3`** (reasoning:low,
  temp 0.35, top_p 0.85, seed 1337, до 3 ретраев). Temperature снижена с 0.7 — на identичных
  фото/повторных анализах был заметный разброс баллов между запусками; seed=1337 сам по себе
  не гарантирует детерминизм (не все провайдеры честно его соблюдают для vision-запросов через
  OpenRouter). Разрешительная к оценке внешности. Фронт и
  профиль шлются **отдельными изображениями** (`body.images`) — `compositeToBase64()` в
  `app.js` существует, но НЕ используется (мёртвый код, оставлен для истории): склейка в одну
  картинку раньше ухудшала оценку джоулайна/носа по профилю, поэтому вернулись к раздельной
  отправке. Язык отчёта — по `lang()`.
  ⚠️ (17-18.07.2026) Замечено в реальном `usage` от OpenRouter: помимо видимого текста ответа
  модель тратит **~700-950 скрытых `reasoning_tokens`** на анализ (оплачиваются как output,
  несмотря на `reasoning: effort='low'`) — TODO проверить, можно ли их отключить/урезать без
  потери качества калибровки (у промпта уже есть свой `INTERNAL STEP`, native-reasoning может
  быть частично избыточен).
- **Оптимизация стоимости (17-18.07.2026):**
  - Фото для ИИ ужимается `oneToBase64()` до **672px** по длинной стороне (было 900px) —
    Grok режет картинку на тайлы 448×448 (256 токенов/тайл, максимум 6 тайлов = 1792 токена);
    при 900px портретное фото почти всегда упиралось в этот потолок, при 672px укладывается в
    меньше тайлов. Живой тест показал реальный расход ~550 токенов на фото (заметно меньше
    теоретического максимума). Визуально проверено — детализация лица (кожа/глаза/челюсть)
    не пострадала. **Карточка результата (`buildShareCard`) не затронута** — она рисуется из
    отдельного `cleanImageCanvas` в оригинальном разрешении, а не из уменьшенной копии,
    которая уходит только в ИИ.
  - В запрос к OpenRouter добавлен `session_id` (`facerate-ru`/`facerate-en`, по языку) —
    для xAI кэширование промпта чувствительно к «server affinity»: без стабильного ключа
    одинаковые запросы могут разлетаться по разным бэкендам и не кэшироваться. Статичная
    калибровочная часть промпта (~2500 токенов) идёт ДО переменных данных (метрики, тизер-
    суффикс), так что теоретически кэшируема целиком. ⚠️ В двух быстрых тестовых запросах
    подряд `cached_tokens` не вырос (остался на 128) — реальный выигрыш от этой правки НЕ
    подтверждён живым тестом, стоит последить на реальном трафике несколько дней, прежде чем
    считать её рабочей.
  - Промпт `callAI` переписан: убраны 2-3 повтора одной и той же мысли («не ставь всем
    5.5-6») и вся служебная/калибровочная часть переведена с русского на английский (кириллица
    токенизируется на 30-40% хуже латиницы при том же смысле; вывод на русском по-прежнему
    гарантирован отдельной инструкцией, ключи меток типа `ОБЩИЙ_БАЛЛ`/`СИММЕТРИЯ` остаются
    кириллицей — их трогать нельзя, по ним парсится ответ). Итог: ~3983 → ~2711 токенов
    промпта по грубой оценке (эта оценка мерила сырой JS-шаблон с плейсхолдерами, не
    отрендеренный текст — трактовать как ориентир на процент экономии, не как точные абсолютные
    цифры; реальный отрендеренный промпт с одним фото 672px даёт `prompt_tokens` в районе
    2900-3000 по факту из живого теста). `comparePrompt()` (Who Moggs) уже был полностью на
    английском, менять не пришлось.
- **i18n:** словарь строк `I18N` в `app.js`, `BL` (бот оплаты) и `SUP` (бот поддержки) в

## Деплой (полностью автоматический, push в master → всё едет само)

- **Сайт:** push в `master` → `.github/workflows/deploy.yml` (официальный Pages-пайплайн:
  `configure-pages` + `upload-pages-artifact` + `deploy-pages`). Публикует ТОЛЬКО статику —
  список файлов/папок зашит в шаге «Stage static site» (включая `vendor`); **при добавлении
  нового файла на сайт дописать его туда**, иначе не задеплоится.
  - ⚠️ env `github-pages` должен разрешать деплой с ветки `master` (Settings → Environments).
  - ⚠️ `deploy-pages` иногда флейкует «try again later» — лечится ре-запуском workflow.
- **Worker:** push с изменением `worker.js`/`wrangler.toml` → `.github/workflows/deploy-worker.yml`
  (`npm i -g wrangler@4` → `wrangler deploy`). Нужен секрет `CLOUDFLARE_API_TOKEN` в GitHub.
  Ручной деплой (если нет доступа к Actions): `npx wrangler deploy` из корня репо.
- Кэш-бастинг: `?v=N` у `style.css`/`app.js` в `index.html` — поднимать при существенных изменениях.

```
Анализ и аккаунты (сайт):     POST /            анализ (OpenRouter)
                               POST /auth        вход через Telegram Login Widget
                               POST /authpoll    вход через t.me/бот?start=код (поллинг)
                               POST /me          статус: квота, кредиты, unlim, доступные способы оплаты
                               POST /buy         создать инвойс: method=stars|rub|crypto
                               POST /sendcard    отправить share-карточку в личку боту оплаты

Бот оплаты (@faceratepay_bot): POST /tg-webhook       pre_checkout_query + successful_payment + меню бота +
                                                       chat_boost (буст канала → +1 анализ)
                               POST /crypto-webhook   вебхук CryptoBot: invoice_paid → начисление
                               POST /lava-webhook     вебхук Lava.top: payment.success → начисление
                               POST /setup-webhook?secret=<TG_WEBHOOK_SECRET>
                                                       разовая перерегистрация вебхука с нужным allowed_updates
                                                       (нужно дёрнуть руками один раз после любого изменения
                                                       набора update-типов, которые слушает бот — Telegram не
                                                       шлёт chat_boost/новые типы без явного allowed_updates)

Бот поддержки (@FaceRateSupport_bot):
                               POST /support-webhook  AI-FAQ, эскалация оператору, панель модератора,
                                                       поиск платежа по ID, админ-список реф-ссылок медийок

Бот медийных партнёров (@FaceRateMedia_bot):
                               POST /media-webhook    привязка реф-кода, самостоятельная статистика
                                                       (переходы/покупки/выручка), для админов — все реф-ссылки

Разовые админ-инструменты (не для регулярного использования):
                               POST /bulk-discount-once  массовая выдача персональной скидки + личное
                                                          уведомление всем известным пользователям, батчами
                                                          (см. «Массовая скидочная рассылка» ниже). Защищён
                                                          ОТДЕЛЬНЫМ секретом BULK_ACTION_SECRET, не тем же что
                                                          остальные роуты — создавался ad hoc под конкретную
                                                          акцию 21.07.2026, не документирован как постоянный
```

Все группы читают/пишут в один и тот же KV `RATE_LIMIT` — поэтому язык, тарифы, логика
начисления шарятся между сайтом и обоими ботами без дублирования.

## Аккаунты, квоты, оплата

- **Вход:** кнопка на сайте → `t.me/faceratepay_bot?start=<uuid>` → бот ловит
  `/start код` → создаёт сессию; сайт поллит `/authpoll`. Без номера телефона.
  Есть и обычный Telegram Login Widget (`/auth`).
- **Квоты (в порядке приоритета):** активный безлимит (`unlim:tgid` = ms-expiry) →
  подписка на канал (`getChatMember`, кэш подписки 5 мин, `isSubscribed`) = **1
  бесплатный анализ/неделю** (ключ `qw:tgid:weekBucket()` — скользящее 7-дневное
  окно от эпохи, не календарная неделя; было 1/день до 12.07.2026) → кредиты
  (`credits:tgid`).
- **Тизер бесплатного отчёта (добавлено 17.07.2026):** бесплатный еженедельный
  анализ полный только для тех, кто хоть раз реально покупал (`everBought:tgid`,
  флаг без TTL, ставится в `recordOrder()` на любой успешный платёж — карта/крипта/
  Stars/Lava, все три способа проходят через эту функцию). Для тех, кто НИКОГДА не
  покупал, свободный анализ — **тизер**: `isTeaser = mode==='free' && !buyer` в
  `analyze()` дописывает к промпту `FREE_TEASER_SUFFIX`, заставляя ИИ вернуть только
  ОБЩИЙ_БАЛЛ + 3 категории (Симметрия/Глаза/Кожа) без остальных 5 и без
  РЕКОМЕНДАЦИЙ, плюс `max_tokens` для этого вызова урезан 2200→900 — реальная
  экономия токенов/бюджета OpenRouter на бесплатниках, не только UX-приём.
  ⚠️ Частота (раз в неделю) **одинаковая** для всех — покупка НЕ ускоряет
  cadence, только делает конкретно этот бесплатный отчёт полным вместо тизера.
  Промокоды (`credits`/`hours` через `redeemPromo`) **всегда полные** — они
  начисляют `credits:tgid`/`unlim:tgid` напрямую и идут через ветки
  `mode==='paid'`/`'unlim'`, тизер-логика применяется только к `mode==='free'` и
  промокодов вообще не касается; `redeemPromo` также не трогает `everBought`.
  На фронте: `data.teaser` (не `data.mode`) решает, показывать ли карточку
  «🔒 Полный разбор закрыт» (`#teaserUpsell` в `index.html`,
  `showTeaserUpsell()`/`hideTeaserUpsell()` в `app.js`) и сохраняется в
  `localStorage.fm-last.teaser` для верного восстановления вида после рефреша.
  Автоотправляемая в Telegram share-карточка (`buildShareCard`) на тизере рисует
  все 8 категорий, но 5 скрытых — размытыми (`ctx.filter = "blur(3px)"`) с
  замочком 🔒 поверх вместо того, чтобы их просто не показывать; подпись под
  баллом — «Полный разбор на facerate.ru» (не «в боте» — полного разбора в
  боте нет, только на сайте).
  Разовый бэкфилл для уже покупавших ДО этой фичи — 59 tgid из `orders:*`
  прогнаны через `wrangler kv bulk put` на `everBought:tgid`, разового
  админ-команды под это не заводили (сделано вручную одной операцией).

  таймером — она истекла 19.07 и цены **не были подняты обратно** (решение
  владельца оставить низкие цены как постоянные, а не как было объявлено в
  канале) — из-за этого один канальный пост оказался технически неточным;
  21.07 частично компенсировано реальным повышением `p1`.

  **Недельная акция (`SALE_ENDS_AT` в `worker.js`, сейчас `2026-07-28T12:00 МСК`):**
  пока `Date.now() < SALE_ENDS_AT`, и бот (`packsKb`), и сайт (`showPaywall`)
  показывают зачёркнутую «старую» цену (`old*`-поля пакета) рядом с текущей —
  но ТОЛЬКО если `old > текущая` (packsKb: `old && old > cur` — для тарифов
  где цена не менялась `old*` равны текущим значениям и зачёркивание не
  рисуется, специально чтобы не повторять предыдущую ошибку с фейковым
  "было/стало" на непоменявшихся тарифах). Таймер обратного отсчёта («🔥 Цены
  недели! До повышения: N дн M ч») показывается всегда пока акция активна,
  независимо от того, у каких тарифов есть реальное `old`. По истечении срока
  зачёркивание/таймер сами перестают показываться — текущие цены остаются как
  обычные, если явно не поменять `PACKS`. Чтобы продлить/закончить акцию —
  поменяй только `SALE_ENDS_AT` и редеплой (`wrangler deploy`).

  (`pendingDiscount`, например от массовой рассылки) `packsKb`/`showPaywall`
  раньше зачёркивали `oldRub`/`oldStars` (цену до недельного повышения)
  рядом с ценой СО СКИДКОЙ — визуально выглядело как «подешевело» на 1 единицу
  вместо «подорожало, но у тебя скидка». Теперь при активной персональной
  скидке зачёркивается именно текущая БАЗОВАЯ цена (`base`), а не `old*`.

  ⚠️ `m1` **намеренно НЕ** Stars-подписка (`type:'sub'`/`subscription_period`) —
  Telegram отдаёт `SUBSCRIPTION_EXPORT_MISSING`, пока подписки Stars не одобрены
  в @BotFather для этого бота. Пока это разовый `type:'unlim', hours:720`. Если
  включишь Stars-подписки в BotFather — можно вернуть `type:'sub', period:2592000`
  для автопродления (комментарий в коде рядом с `PACKS.m1`).

- **Способы оплаты** — стакаются по наличию секретов (`enabledMethods(env)`):
  - **Stars (XTR)** — всегда доступен, через `createInvoiceLink`/`sendInvoice`.
  - **Крипта** — CryptoBot (Crypto Pay API), включается наличием `CRYPTOBOT_TOKEN`.
    Цена берётся в рублях (`pack.rub`), CryptoBot сам показывает курс в крипте.
  - **Карта РФ** — приоритетно через **Lava.top** (см. отдельный раздел ниже); если
    `LAVA_API_KEY`/`LAVA_OFFER_IDS` не заданы — автоматический откат на ЮKassa через
    Telegram (`YUKASSA_PROVIDER_TOKEN`, требует юрлицо/ИП/самозанятость для регистрации
    в @BotFather, поэтому пока не используется). Один и тот же способ `method:'rub'`
    на фронте — какой провайдер за ним стоит, решается на бэкенде автоматически
    (`lavaConfigured(env)`), UI менять не нужно.
  - И сайт (`app.js`, `showPaywall`), и бот оплаты (`methodKb`/`packsKb`) сначала
    спрашивают **способ**, потом показывают **тариф** в цене этого способа.

- **Меню бота оплаты** (inline-кнопки): статус / магазин (способ→тариф) / мои заказы /
  промокод / **моя реферальная ссылка** / подписка (авто-продление вкл/выкл) /
  розыгрыши / язык / **поддержка** (ссылка на бот поддержки).
- **Рассылка всем пользователям (добавлено 13.07.2026):** `/broadcast ТЕКСТ` в главном
  боте (только `ADMIN_USERNAMES`) — собирает уникальные tgid из всех KV-следов
  (`collectAllUserIds()`: префиксы `user:`, `orders:`, `unlim:`, `credits:`, `lang:`,
  `qw:`) и рассылает текст каждому с троттлингом ~40мс между сообщениями, в конце
  репортит сколько отправлено/не доставлено (заблокировали бота и т.п.). ⚠️ Полное
  покрытие аудитории гарантировано только для новых сообщений после 13.07.2026 (когда
  появился `user:tgid`) — более старые «молчаливые» пользователи без покупок и без
  недавней free-квоты в выборку могут не попасть, это best-effort backfill, а не
  надёжный список подписчиков.
- **Промокоды:** полностью на кнопках через панель админа в боте поддержки (⚙️ Admin →
  промокоды) — выбор типа (`credits`/`hours`/`discount`/`refcode` — «засчитать
  покупку медийке»), суммы, числа активаций, всё кнопками, без ручного ввода команд.
  Один код — один раз в руки на пользователя. Это же механика розыгрышей (кидаешь код
  в канал).
- **Буст канала → +1 анализ:** бустнул `@wwwfacerateru` (Telegram Premium boost) →
  автоматически +1 бесплатный анализ, один раз на человека (`boosted:tgid` в KV,
  снятие/повторная установка буста не даёт зафармить ещё раз). Требует: (а) бот —
  админ канала, иначе Telegram вообще не пришлёт событие `chat_boost`; (б) вебхук
  зарегистрирован с `allowed_updates`, включающим `chat_boost` (см. `/setup-webhook`
  выше — Telegram не шлёт этот тип обновлений по умолчанию).

## Реферальная система (два вида ссылок)

**1. Персональная ссылка (у каждого пользователя, самостоятельно в главном боте)**
- Кнопка «🔗 Моя реферальная ссылка» в `@faceratepay_bot` — код создаётся один раз на
  аккаунт (`myrefcode:tgid` → `ref:<CODE>` с флагом `personal:true, ownerTgid`).
- ⚡ (13.07.2026) Награда теперь **мгновенная и взаимная**: как только друг ПЕРВЫЙ РАЗ
  открывает бота по ссылке (`/start ref_CODE` → `attributeReferral()`), **и он, и владелец
  ссылки сразу получают по +1 анализу** — без покупки, без условий. Раньше было: только
  владельцу, и только после того как приглашённый что-то купит (менее вирально, награда
  друга отсутствовала вовсе — это и была причина смены механики). Друг получает отдельное
  уведомление о бонусе прямо в приветственном сообщении бота.
- Как только по ссылке в сумме прошло **5 покупок** (константы
  `PERSONAL_REF_DISCOUNT_THRESHOLD`/`_PCT`/`_OWNER_DISCOUNT_PCT` в `worker.js`):
  дальнейшие покупатели по ссылке получают скидку **10%**, а сам владелец — скидку
  **15%** на свои собственные покупки (в любом боте/способе оплаты).
- Самому себе по своей же ссылке засчитать покупку нельзя (проверка в
  `attributeReferral`/`trackReferralPurchase`).
- Такие коды **не показываются** в админ-панели медийных ссылок
  (`nonPersonalRefCodes()` фильтрует по `personal:true`), иначе список зарастёт
  сотнями пользовательских кодов.

**2. Медийная ссылка (создаёт админ вручную, для блогеров/партнёров)**
- Админ создаёт код в боте поддержки (⚙️ Admin → реферальные ссылки), задаёт %
  комиссии медийке (`pct`, от фактически уплаченной суммы **с учётом скидки
  покупателя**, не от номинала прайса) и опционально % скидки покупателю (`buyerPct`).
- Партнёр сам привязывает свой код в `@FaceRateMedia_bot` (`refowner:CODE`/
  `refowned:tgid`) и там же смотрит статистику в реальном времени — переходы,
  покупки, накопленная выручка/комиссия — без необходимости спрашивать у владельца
  отчёт вручную.
- При создании ссылки админу автоматически приходит готовый текст-инструкция для
  партнёра (с реальными ссылкой/кодом/%) — просто скопировать и отправить.

**3. Медиа-промокод (`promo.mediaPct`) — изолирован от реф-ссылок, для тех же партнёров**
- Отдельная сущность в `promo:<CODE>` (НЕ `ref:<CODE>`): `mediaPct` (% партнёру),
  `discount` (% скидки покупателю, опционально), свои `revenueRub`/`purchases`.
- Активация в главном боте ставит `pendingMediaPromo:tgid` (24ч, одноразово) — при
  следующей оплате `trackMediaPromoPurchase()` начисляет комиссию НАПРЯМУЮ на этот
  промо-объект и **полностью пропускает** обычную ref:-систему (`trackReferralPurchase`
  для этой покупки не вызывается вовсе) — так одна покупка не может быть зачтена
  дважды двум разным источникам.
- Создаётся либо админом (Admin → Промокоды → «📣 Медиа-промо»), либо **самим
  партнёром** в `@FaceRateMedia_bot` («➕ Создать промокод») — но % партнёр себе не
  выбирает, он всегда наследуется от его уже привязанного `ref:<CODE>` (`ref.pct`),
  сам партнёр вправе задать только скидку покупателю (0-30%) и текст кода.
- Управление у админа: Admin → Промокоды → «🗑 Управление кодами» (изменить
  количество активаций/удалить, работает и для старых кодов) и «📜 История вводов»
  (кто и когда активировал какой код).
- ⚠️ Старый механизм `promo.refcode` (промокод, переключающий `pendingRefCode` на
  чужую `ref:`-ссылку) **удалён 09.07.2026** — заменён на `promo.mediaPct` полностью;
  оставшиеся на тот момент коды перенесены через одноразовую admin-кнопку
  «🔁 Перенести старые медиа-промо» (`migrateOldMediaPromos()`), с сохранением
  накопленных purchases/revenueRub.

Общая инфраструктура (`ref:<CODE>` в KV, `attributeReferral`/`trackReferralPurchase`
в `worker.js`) используется для видов 1 и 2 — отличаются только флаг `personal` и то,
как считается награда (фиксированный кредит vs % от выручки). Вид 3 (медиа-промокод)
намеренно НЕ переиспользует `ref:` — это отдельная простая структура без кликов/
атрибуции по ссылке, только по факту ввода кода.

## Розыгрыш (добавлено 12.07.2026)

Отдельная сущность `giveaway:current` в KV — `{id, endTs, credits, winners, entries}`.
Один активный розыгрыш одновременно.

- **Запуск (админ, в главном боте):** `/newgiveaway ПОБЕДИТЕЛЕЙ АНАЛИЗОВ ДНЕЙ`
  (например `/newgiveaway 3 5 7`) — создаёт розыгрыш и сразу присылает готовый
  текст поста для канала с диплинком `t.me/faceratepay_bot?start=giveaway`
  (кнопку-ссылку добавляешь через редактор кнопок Telegram при публикации поста).
- **Участие:** диплинк/кнопка «🎉 Розыгрыши» в меню → карточка розыгрыша с кнопкой
  «🙋 Участвовать» → **живая** (не кэшированная, `isSubscribed(env, tgid, true)`)
  проверка подписки на канал. Не подписан → просьба подписаться и нажать ещё раз.
  Подписан → добавлен в `entries` (один раз, повторный клик просто показывает
  «уже участвуешь»).
- **Розыгрыш подводится САМ**, без ручных действий: Cron Trigger (`[triggers]` в
  `wrangler.toml`, раз в час `0 * * * *`) → `scheduled()` в `worker.js` →
  `checkGiveawayDraw()` → если `endTs` истёк, вызывает `runGiveawayDraw()`:
  случайно выбирает победителей из `entries`, но **перед начислением каждому ещё
  раз живьём проверяет подписку** — если человек успел отписаться, он пропускается
  и заменяется следующим случайным участником из пула. Начисляет `credits`,
  лично уведомляет каждого победителя, закрывает розыгрыш, шлёт всем админам
  (`SUPPORT_ADMIN_ID`) готовый пост-отчёт для канала.
- **Досрочно/вручную:** команда `/drawgiveaway` делает то же самое немедленно
  (обычно не нужно).
- Диплинк `/start shop` — открывает сразу шаг выбора способа оплаты (минуя меню),
  используется в промо-постах о ценах вместо ссылки на сайт.

**Скидка у покупателя — всегда одна, никогда не суммируется**: `buyerDiscountPct()`
возвращает `pendingDiscount` (промокод) с абсолютным приоритетом, иначе `Math.max()`
по возможным ref-источникам — сложения никогда не происходит, это проверено и
специально сохраняется при любых будущих правках этой функции.
- **Лимиты-страховки:** `IP_LIMIT_DAY=40` (касается всех, включая оплативших).
  `GLOBAL_DAILY_CAP=3000` — потолок **только для бесплатного тира** (защита бюджета
  OpenRouter от наплыва трафика); проверяется **после** определения режима и не
  блокирует тех, у кого активны кредиты/безлимит — оплативший всегда получает доступ,
  даже если у бесплатных закончился дневной лимит.

## Оплата картой РФ через Lava.top

Lava.top выбран вместо ЮKassa, так как позволяет принимать платежи физлицу без
регистрации ИП/самозанятости.

- **Как это работает:** товар в личном кабинете Lava.top создаётся с флагом
  **«Цена по запросу через API»** (`isDynamicPrice:true` — без этого их Public API
  вообще не видит товар, это недокументированный нюанс их интерфейса). Ключевое
  следствие, которое раньше было упущено в коде: у динамических офферов **саму
  цену задаёт КАЖДЫЙ запрос** — сумма из каталога Lava.top (которую видно в их
  личном кабинете) не обязана совпадать с тем, что реально спишется, и её не
  нужно вручную синхронизировать. `createLavaInvoice()` сначала проверяет флаг
  `isDynamicPrice` через `lavaOfferIsDynamic()` (`GET /api/v2/products`), и если
  он есть — просто передаёт `pack.lavaRub` из `PACKS` в `body.amount` при
  `POST /api/v3/invoice`. Поменять цену карты/СБП = поменять число в `PACKS` и
  задеплоить, кабинет Lava.top трогать не нужно.
  Реального email у пользователей нет (вход только через Telegram) — используется
  синтетический `tg<tgid>@facerate.ru`, из которого `tgid` потом парсится обратно
  в вебхуке (`lavaWebhook` в `worker.js`) — без своей БД соответствий.
- **Вебхук:** аутентификация — **Basic Auth** (`LAVA_WEBHOOK_LOGIN`/`LAVA_WEBHOOK_PASS`,
  задаются при создании вебхука в личном кабинете Lava.top: Интеграции → API →
  Webhook → тип аутентификации **Basic**, не «API key вашего сервиса» — так надёжнее,
  это стандартный RFC 7617, а не гадание про формат кастомного заголовка).
- **Маппинг тариф → оффер:** `LAVA_OFFER_IDS` — JSON `{"p1":"uuid",...}`, все 5
  тарифов настроены (включая `h1`, добавлен 12.07.2026). Чтобы посмотреть текущий
  каталог офферов Lava.top (id/название/динамическая ли цена) без похода в их
  личный кабинет — админ-команда бота `/lavaproducts` (доступна только
  `ADMIN_USERNAMES`), выводит и сам каталог, и текущий `LAVA_OFFER_IDS` рядом —
  полезно при добавлении нового тарифа: сначала создать товар в кабинете
  Lava.top с флагом «цена по запросу», потом взять его offer id из `/lavaproducts`
  и дописать в секрет `LAVA_OFFER_IDS`.
  ⚠️ Вебхук Lava.top шлёт `product.id` (ID ТОВАРА), а не оффера —
  `LAVA_OFFER_IDS` хранит ID ОФФЕРА (нужен для `/invoice`), поэтому напрямую
  сравнивать нельзя. `lavaPackIdByProductId()` матчит через каталог (`GET
  /api/v2/products?feedVisibility=ALL`), перебирая ВСЕ офферы товара (не только
  первый — иначе матч не находится, если `LAVA_OFFER_IDS` указывает на другой
  оффер того же товара). Тип события в вебхуке — `payment.success`; проверка от
  повторного начисления — `lavapaid:<contractId>` в KV, **выставляется только
  после** успешного распознавания покупателя/тарифа (иначе нераспознанный платёж
  тихо теряется навсегда без шанса на ретрай).
- **СБП:** `paymentProvider:'PAY2ME', paymentMethod:'SBP'` в теле `/invoice` — даёт
  отдельный провайдер (не дефолтный `SMART_GLOCAL`, который только карта) с реальным
  QR-кодом СБП. Недокументировано в обычных доках Lava.top, найдено через их
  OpenAPI-спеку `gate.lava.top/docs/documentation.yaml`.
- `LAVA_MIN_RUB = 50` — минимальная сумма инвойса Lava.top; скидки клэмпятся снизу
  этим значением (`Math.max(LAVA_MIN_RUB, ...)`), иначе Lava.top отклоняет запрос.
  Все тарифы сейчас дороже 50₽, так что это пока чисто страховка на будущее — но
  если когда-нибудь появится тариф ровно в 50₽, скидка на карту/СБП для него будет
  технически неприменима ни при каком %; список тарифов (`packsKb` в `worker.js`)
  в этом случае покажет честно `«без скидки — минимум платёжки»` вместо цены,
  которая по факту не спишется (иначе выглядит как баг «скидка не сработала»).

## Бот техподдержки (@FaceRateSupport_bot)

Отдельный Telegram-бот, отдельный токен, но тот же воркер и тот же KV.

- **AI-first:** любое сообщение пользователя без активной эскалации уходит в
  `supportAI()` (OpenRouter, `x-ai/grok-4.3`, системный промпт `SUP_FAQ` с фактами
  о сервисе). Ответ + кнопки «Позвать оператора» / «← Меню».
- **`/start`, `/menu`:** меню — FAQ / Позвать оператора / Открыть сайт / Купить
  (ссылка в бот оплаты) / смена языка / (только для админов) кнопка **⚙️ Admin**.
- **Несколько админов:** `SUPPORT_ADMIN_ID` — один id **или несколько через запятую**
  (`adminIds()`/`isAdminId()` в `worker.js`). Эскалации и уведомления рассылаются
  всем перечисленным; `supmap` (старый reply-flow) хранится отдельно на каждого
  админа (`supmap:<adminChatId>:<messageId>`), чтобы не путались при двух и более
  модераторах одновременно.
- **Всё на кнопках, без команд:** админам при `/start` закрепляется **постоянная
  клавиатура** снизу экрана с кнопкой **«⚙️ Admin»** (`adminReplyKb()`) — не пропадает
  между сообщениями, поэтому `/admin` и `/close` вводить руками не нужно никогда.
- **Эскалация:** кнопка «🧑 Позвать оператора» ставит `suphuman:<uid>` (сутки) —
  дальше все сообщения юзера идут всем админам и попадают в список открытых тикетов.
- **Панель модератора** (кнопка ⚙️ Admin, видна только админам):
  - **📂 Открытые чаты** — кнопка на каждого юзера с превью последнего сообщения.
    Тапнул → следующий обычный текст (без реплая!) уходит именно этому юзеру,
    пока не откроешь другой чат или не закроешь этот («✖» рядом с чатом).
    Старый способ (реплай на пересланное сообщение) тоже по-прежнему работает.
  - **💳 Транзакции** — последние 20 из лога всех платежей (Stars/крипта/карта):
    время, кто, какой пакет, сумма, способ, короткий **ID заказа**.
  - **🔍 Найти платёж по ID** — покупатель называет ID заказа (виден ему в «Мои
    заказы» и в сообщении об успешной оплате) → `findOrderById()` ищет в `translog`
    (последние 50) и подтягивает username/имя покупателя через `getChat`.
  - **🔗 Реферальные ссылки** — список медийных ссылок (без персональных, см. выше),
    создание новых, правка % комиссии/скидки.
  - **🎁 Промокоды** — создание кнопками (тип/сумма/число активаций), список активных.

## Как проверить, что платёж реально даёт доступ (шпаргалка для дебага)

```bash
NS=<id из wrangler.toml>
# 1) создать тестовую сессию
npx wrangler kv key put --remote --namespace-id=$NS "sess:TESTTOKEN" \
  '{"id":999000001,"first_name":"T","username":"","photo_url":""}'
# 2) выдать безлимит (как это делает grantPack после оплаты)
npx wrangler kv key put --remote --namespace-id=$NS "unlim:999000001" "$(( ($(date +%s)+2592000)*1000 ))"
# 3) проверить статус и сам анализ
curl -s -X POST https://api.facerate.online/me \
  -d '{"token":"TESTTOKEN"}'
curl -s -X POST https://api.facerate.online/ \
  -d '{"token":"TESTTOKEN","prompt":"Ответь одним словом: работает?"}'
# 4) убрать за собой
npx wrangler kv key delete --remote --namespace-id=$NS "sess:TESTTOKEN"
npx wrangler kv key delete --remote --namespace-id=$NS "unlim:999000001"
```
⚠️ `wrangler kv key put` без `--remote` пишет в локальную эмуляцию, а не в боевой KV — легко потерять час на «почему изменения не видны».

## Фичи фронта

- **Поток:** гейт языка (первый визит) → интро → лендинг → полноэкранное меню
  (3D-пилюля за курсором) → анализ.
- **Анализ:** скан-анимация (локально, бесплатно) → пейволл (если нет квоты, способ→тариф) → отчёт.
- **Who Moggs?** («кто моггает», НЕ «моггит» — грамматически неверная форма, явно
  запрещена в промпте): плитка меню → два лица → вердикт «A MOGS B» + карточка с
  красной плашкой **MOGGED** на глазах проигравшего (1 кредит). Заголовки фичи всегда
  на английском независимо от языка сайта. Пока идёт распознавание лица (первая
  загрузка MediaPipe может занять время) — золотая линия сканирования поверх
  превью фото; сам AI-запрос сравнения показывает тот же HUD с прогресс-баром и
  фазами, что и обычный анализ (`startAIHUD`/`stopAIHUD` теперь принимают id
  контейнера — общий код на обе HUD-карточки, которые одновременно есть в DOM).
- **Обратная связь** (`feedback.html`): оценки 1-10 по дизайну/функциям/качеству
  анализа + свободный текст + чекбокс «хочу сотрудничать» → ответы падают админу в
  Telegram (`SUPPORT_ADMIN_ID`), даёт +1 бесплатный анализ один раз на аккаунт
  (`feedbackDone:tgid`). Своя мини-реализация Telegram-логина (код+поллинг),
  устойчивая к тому, что встроенный браузер Telegram может убить JS-контекст на
  полпути — код входа переживает это через `localStorage` и доигрывается сам при
  возврате на страницу.
- **Share-карточка** (`buildShareCard`, `buildCompareCard`): кроп по рамке лица
  (`window._fmFaceBox` — координаты **в пикселях**, не нормализованные 0..1, это уже
  однажды было багом), бренд-пилюля, бары, POTENTIAL. Share + Send to TG (`/sendcard`).
- Дерзкий режим (роаст), история оценок (localStorage `fm-*`), звук/музыка.

## Формат ответа ИИ (критично для парсинга)

Анализ: `parseAIReport` ждёт русские метки `ОБЩИЙ_БАЛЛ:`, `СИММЕТРИЯ:`,
`ГЛАЗА_CANTHAL_TILT:`, `МИДФЕЙС_MAXILLA:`, `ДЖОУЛАЙН_MANDIBLE:`, `НОС_NOSE:`,
`ГУБЫ_СКУЛЫ:`, `КОЖА:`, `ГРУМИНГ_STYLE:`, `РЕКОМЕНДАЦИИ:`. **Ключи не переводить** —
меняется только язык описаний. Балл — дробный (промпт запрещает целые/`.0`), разброс
≥2.5 между категориями.

Сравнение (`comparePrompt`/`parseCompare` в `app.js`): `SCORE_A` / `SCORE_B` /
`TRAITS_A` / `TRAITS_B` (по 3 черты через `;`) / `WINNER` / `VERDICT` (2-3 предложения
с опорой на конкретные черты, не общая фраза) / `CAT_<KEY>: A=0.0 B=0.0` — 8 категорий
для обоих лиц (те же ключи, что в `CMP_CATS`). ⚠️ `VERDICT`-регулярка обрезает текст на
первой строке `CAT_` ИЛИ на пустой строке — если модель не ставит перенос перед CAT_
блоком, весь список категорий раньше склеивался с текстом вердикта на share-карточке
(баг, исправлен 09.07.2026). Если меняешь формат промпта — не убирай `\n\s*CAT_` из
регулярки `vm` в `parseCompare`, иначе баг вернётся.
Промпт также явно требует: если A и B — одно и то же лицо, ставить идентичные баллы
и писать об этом в начале VERDICT (снижает разброс на повторных/одинаковых фото).

  внутренний low-stakes инструмент, не платёжные данные) и `ptasks:CODE` (JSON-массив

## Гайд + ведение 90 дней (пак `guide`, 399 ₽ / 279 ⭐ на запуске)

Отдельный продукт: PDF-гайд на 26 страниц + личный раздел на сайте + задания
от бота. Покупается как обычный пак, но выдаёт не кредиты, а доступ.

**Цены.** `rub: 399, stars: 279`, зачёркнутые `oldRub: 999, oldStars: 749`.
Зачёркивание рисуется по флагу `launch: true` в `PACKS.guide` независимо от
недельной акции (`SALE_ENDS_AT`), потому что та давно истекла. Закончить промо =
убрать `launch` и поднять `rub`/`stars` до значений `old*`. Сайт берёт обе цены
из ответа воркера (`/progress` возвращает `pack: PACKS.guide`), поэтому менять
цену надо только в одном месте.

**Что даёт покупка** (`grantPack`, ветка `type === 'guide'`):
- PDF файлом в бот через `sendDocument` по `GUIDE_FILE_ID` (файл живёт в Telegram,
  хостить ничего не надо);
- `guide:{tgid} = '1'` — доступ к разделу «Ведение», бессрочно;
- +5 обычных анализов на счёт;
- `gstart:{tgid}` — точка отсчёта плана, от неё считаются недели;
- добавление в `guidelist` — список получателей еженедельной рассылки.

**Замеры прогресса.** Обычный `/`-эндпоинт с флагом `measure: true`. Идут МИМО
free-квоты и кредитов, ограничены отдельно: один раз в 10 дней (`PROG_COOLDOWN`),
максимум 60 (`PROG_MAX`). Замер раньше срока возможен за 1 анализ — фронт
повторяет запрос с `forcePay: true`. Замеры по расписанию бесплатны намеренно:
в плане три обязательные контрольные точки, и брать за них деньги значило бы
продавать план, которым нельзя пользоваться без доплаты.

**Отдельный промпт.** Замер использует `buildMeasurePrompt`, а НЕ основной
откалиброванный промпт оценки: задача другая — сравнить два состояния и отделить
реальное изменение от разницы съёмки. Промпт доводился шестью живыми прогонами,
и каждый находил то, чего не видно при чтении кода:
- советовал жвачку для челюсти, хотя гайд, который мы же продаём, разбирает её
  как вредную (расширяет низ лица, риск для ВНЧС, и RCT 2024 показал, что форма
  лица не меняется);
- назначал кислоту дважды в день на всё лицо, вопреки правилу «один актив за раз»
  из того же гайда;
- дословно копировал собственный прошлый отчёт, потому что `buildMeasurePrompt`
  подставлял его целиком ПОСЛЕ описания формата;
- уйдя от выдумок, скатился в «параметр не управляем» по половине пунктов;
- не распознавал селфи, хотя гайд прямо пишет, что фронталка искажает нос и мидфейс.

Позже вскрылось ещё два случая того же рода:
- на ДРУГОМ фото возвращались те же восемь баллов до десятой доли — модель видела
  прошлые оценки в промпте и переписывала их. Помогло только убрать все «X/10»
  из прошлого отчёта: теперь она видит лишь словесное описание, а числа остаются
  у воркера, который сам считает разницу;
- фраза «за N дней заметный сдвиг маловероятен» работала как указание, а не как
  контекст, и подталкивала к «ничего не изменилось» независимо от фото.

Вывод, важный для правок: **промпт понимает списки и не понимает принципы, а любое
ожидание, высказанное вслух, он исполняет.** Не работает «не якорись» — работает
не показывать цифры. Не работает «не выдумывай» — работает список запрещённого.

Отдельное поле `ТОТ_ЖЕ_ЧЕЛОВЕК` (ДА / НЕ УВЕРЕН / НЕТ): раньше чужое лицо молча
считалось тем же человеком без прогресса. При вердикте `НЕТ` замер **не пишется
в `prog:`** вообще, чтобы не портить график и все последующие сравнения. Причёска,
вес, свет, борода и очки в промпте явно названы как то, что меняется у одного
человека — иначе модель начинает видеть подмену в каждой новой стрижке.

**Что хранится.** Только `prog:{tgid}` (дата, баллы, оценка съёмки),
`progtxt:{tgid}` (последние 3 полных текста для сравнения) и `tips:{tgid}`
(рекомендации, разложенные по категориям). **Фотографии не хранятся нигде** —
ни на сервере, ни в браузере: это биометрия по 152-ФЗ, и `privacy.html` прямо
обещает их не хранить. Коллаж «до/после» собирается на canvas из двух снимков,
которые человек выбирает в момент сборки.

**Задания бота.** `progressCron(env)` в общем часовом кроне. Раз в 7 дней от
`gstart` шлёт задание недели со ссылкой на главу гайда и страницу; на 6-й день
спрашивает «сделал?» двумя кнопками (`wk:1:N` / `wk:0:N`) и ведёт серию
(`streak:`/`best:`); когда прошли 10 дней — напоминает о замере, не чаще раза
в 3 дня.

**Персональный совет в задании.** ИИ размечает рекомендации категориями
(`[КОЖА] текст`), они раскладываются по восьми параметрам. Совет для недели
подбирается **по смыслу задания** (`WEEK_WORDS`), а не по параметру: неделя про
сон должна получить совет про сон, даже если модель записала его в «симметрию».
Если ничего не совпало — берётся самый слабый параметр с честной подписью
«твоё слабое место сейчас». Если и этого нет — совета не будет вовсе, случайный
текст под заголовком «лично тебе» хуже, чем его отсутствие.

**Раздел на сайте.** Плитка «Ведение» в меню → `renderProgress()` переносит
скрытую секцию `#progressSection` в `#fsBody`. Ссылка на секцию держится в
замыкании: `openView()` чистит `body.innerHTML` перед отрисовкой, иначе секция
исчезала при втором открытии. Данные — `POST /progress`.

Грабли, на которые уже наступили при интеграции (не повторять):
- `app.js` подключается ДО разметки секции, поэтому все слушатели внутри неё
  только делегированные от `document`;
- при выносе стилей из демо туда утёк глобальный `*{margin:0;padding:0}`,
  `body{}` и `prefers-reduced-motion` — это ломает вёрстку всего сайта, всё
  должно быть под `#progressSection`;
- сброс полей обязан быть в `:where()`, иначе специфичность ID перебивает
  компонентные правила (так подзаголовок терял центрирование);
- `index.html` пинит `app.js?v=NN` и `style.css?v=NN` — **при любой правке этих
  файлов версию надо поднимать**, иначе браузеры отдают старую копию;
- Pages-workflow копирует в `_site` **явный список файлов**: всё новое (было с
  `guide-web.json` и `img/`) надо вписывать в `.github/workflows/deploy.yml`,
  иначе файл лежит в репозитории и отдаёт 404;
- фото замера обязано идти через `oneToBase64(img, 672)`; сырой файл с телефона
  в base64 не доходит до воркера, и это выглядит как «сеть не ответила»;
- `analyze()` не требует `body.prompt`, когда стоит `measure: true` — промпт
  строит воркер. Раньше запрос отбивался на входе и возвращал ТЕКСТ, а не JSON;
- ответы воркера читать через `r.text()` + осторожный `JSON.parse`: часть ошибок
  приходит простым текстом, и `r.json()` на них падает, пряча настоящую причину;
- кнопку замера **нельзя блокировать** на время кулдауна: досрочный замер за
  анализ становится недостижим, потому что модалку не открыть.

**Админские команды:** `/testgrant guide` — выдать пак себе без оплаты (зовёт
настоящий `grantPack`, проверяет всю выдачу кроме приёма денег);
`/lavaproducts` — каталог Lava.top и текущий `LAVA_OFFER_IDS`. Отправка боту
любого документа админом возвращает его `file_id` (нужно для `GUIDE_FILE_ID`,
т.к. `getUpdates` недоступен при активном вебхуке).

## Пилюля: почему это картинка, а не 3D (09.08.2026)

На лендинге и в меню стояли два `<model-viewer>` с `auto-rotate`. Пока они в
кадре, WebGL рисует непрерывно, а стоят они в меню — там, где человек и тыкает.
Полевые данные Google показали, что единственная метрика Core Web Vitals,
которую сайт не проходит, это **INP (266 мс)**, то есть отзывчивость, а не
загрузка: LCP 1.9 с, CLS 0.07, TTFB 0.6 с — всё зелёное.

Теперь `assets/pill3d/pill.webp`: 180 кадров, 14 с на оборот, 285 КБ. По весу
это примерно как библиотека `model-viewer` (254 КБ), которую заменили, — выигрыш
не в байтах, а в свободном главном потоке.

Кадры снимает `_pill-harness.html` (в сборку сайта не входит) через headless
Chrome. Две грабли, обе стоили времени:

- `toDataURL` гонится с собственным циклом отрисовки model-viewer и отдаёт
  пустые кадры. Поэтому стенд кладёт на страницу по экземпляру на ракурс и
  снимает обычный скриншот.
- Индикатор прогресса в углу страницы попал в правый нижний тайл сетки, и ровно
  9 кадров из 180 уехали с зелёной полосой поперёк. Прогресс теперь только в
  `document.title`, куда скриншот не дотягивается. Если будешь пересобирать —
  проверяй кадры на посторонние пиксели, глазами это ловится плохо.

Пересобрать: поднять локальный сервер, прогнать стенд с `?n=180&list=...`,
очистить, склеить `img2webp -loop 0 -d 78 -lossy -q 60`. Уменьшать разрешение
бесполезно: при масштабировании файл РАСТЁТ (сглаживание убивает совпадение
соседних кадров, на котором держится сжатие анимации).

## Ветка `nivx-optimizations` (влита в `lean-report`)

Разбор конкурента `nivx.ru`, который держит 3 ₽ за анализ на том же стеке
(MediaPipe, IMAGE-режим, фото 720px). Экономия у него не в модели, а в том, что
модель почти ничего не пишет: пропорции и ранг он считает в браузере, а видео
собирает через WebCodecs + `mp4-muxer` без участия сервера.

В ветке лежит первый пункт: `computeProportions()` и `pslTier()` считают шесть
отношений и тир по 468 точкам, блок `#propBlock` и бейдж `#tierBadge`. Кроме
цены токенов это чинит стабильность: геометрия даёт одно и то же число для
одного лица, а модель каждый раз новое.

**Уточнение 13.08.2026.** Раньше здесь было записано, что nivx отдаёт шаблонные
тексты по баллу. Это неверно: в его клиентских чанках всего 30 русских строк, и
все до одной — интерфейс, фазы загрузки и ошибки. Прозу пишет модель, просто
отчёт короткий (~120 слов), а вокруг насыпано под сорок посчитанных в браузере
чисел. Ранг у него — обычный `if` по баллу (TRUE ADAM ≥9, CHAD ≥8, MTN ≥7,
LTN ≥6, SUB 5 ≥3), MediaPipe вшит в бандл. Покупка без входа работает живьём:
на первой загрузке уходит `POST /api/backend/auth/device`.

Не сделано: JSON вместо прозы (обезличит отчёт, а мы продаём именно текст),
покупка без входа через устройство — она упирается в то, что платёж в lava.top
сопоставляется с выдачей по email вида `tg{id}@`, и трогать это до конца
проверки аккаунта нельзя.


## Вход через Telegram: почему ключ в KV меняет имя (09.08.2026)

Сайт открывает `t.me/бот?start=КОД` и опрашивает `/authpoll`. Раньше он спрашивал
одно и то же имя ключа, и вход занимал до минуты.

Причина: **KV кеширует в колокации и ответ «ключа нет» тоже**, а `cacheTtl` ниже
60 секунд не опускается. Первый же опрос уходил в момент, когда человек только
переключался в Telegram и нажать ничего не успел; промах кешировался, и вход
случался не когда нажали Start, а когда протухал кеш.

Поэтому имя ключа теперь меняется каждые `AUTH_BUCKET_MS` (10 с): бот пишет код
сразу в `AUTH_BUCKETS` будущих корзин, а поллинг спрашивает текущую — её он ещё
не трогал, значит получит ответ мимо кеша. Корзина считается по часам Cloudflare
с обеих сторон, время на устройстве роли не играет. Первый опрос убран: он
ничего не проверял, зато портил текущую корзину. Худший случай стал 9.5 с,
типичный около 5.

## Гайд: что переписано 09.08.2026

Глава про кожу выросла с трёх страниц до четырёх и идёт так: определение типа
кожи (тест на два часа) → три базовых шага → отдельная страница про защиту от
солнца → акне → готовая рутина.

Решения, которые стоит помнить при правках:

- **Ретиноиды убраны намеренно.** Схема зависит от типа кожи и от того, что
  человек уже использует, значит это к дерматологу, а не в гайд для
  восемнадцатилетних. Салициловая кислота осталась, точечно.
- **SPF привязан к УФ-индексу, а не к календарю.** «Мазаться круглый год» для
  средней полосы неверно: при индексе 0–2 можно не наносить.
- **Иллюстрация схематичная и подписана как схема.** Реальные снимки «до и
  после» (тот самый водитель грузовика из NEJM) защищены авторским правом.
- Умные слова убраны: «себум» заменён на «жир» и подобное. Аудитория — парни
  18 лет, которые про уход не знают ничего.

Стилевой проход по всему тексту: тире с пробелом было 152, стало 18, и почти
все оставшиеся это пустые клетки трекера. Убраны обороты, которые читаются как
машинные.

**Врезки залиты плоским цветом, а не градиентом.** Градиент `linear-gradient(90deg,
…, transparent 88%)` при печати в PDF Chrome разбивает на куски, и по середине
каждой врезки шёл видимый шов. Побочный эффект: врезки перестали растрироваться,
PDF похудел с 4.6 МБ до 2.1 МБ.

После правки гайда нужно: пересобрать `guide-web.json` (веб-версия на сайте),
пересобрать PDF через headless Chrome, **перезалить файл в бота и обновить
`GUIDE_FILE_ID`** — иначе покупателям уходит старая сборка.


## Проверка аккаунта в lava.top (11.08.2026)

Сначала модерация отклонила товар с гайдом («нет платного контента в
продукте»), затем служба безопасности запросила доказательства, что клиенты
получают оплаченное. Причина одна и та же: **в карточках товаров не заполнена
платная часть**, а мы доставляем сами через бота и личный раздел сайта.

**Где брать доказательства.** Журнал транзакций лежит в KV под ключом
`translog` (последние 3000 записей, пишет `recordOrder`). На момент проверки:
118 оплат картой с 26.07.2026 на 9881 ₽.

Самый сильный аргумент оказался не в самих оплатах, а в **потреблении**: у
покупателей пака `p1` остаток `credits:{tgid}` нулевой, то есть купленное
израсходовано, а часть покупателей возвращается за второй покупкой в тот же
день. Любой платёж сопоставляется с выдачей по трём полям: время, сумма и
email вида `tg{id}@`, который мы сами подставляем в счёт Lava.

Отправили: записи экрана полного цикла по каждому типу товара, скриншот
журнала транзакций, ссылку на оферту, сам PDF.

**Три формальные дыры, найденные при разборе и НЕ исправленные:**

1. Оферта (`terms.html`, раздел 5) описывает только разовые анализы и безлимиты
   на сутки и месяц. Слова «гайд» в документе нет — продаём товар, которого нет
   в договоре.
2. В оферте не указан продавец: ни статус, ни имя, ни ИНН, ни адрес для
   претензий. Для публичной оферты это существенный пробел, и документ мы им
   отправили.
3. Зачёркнутые 999 ₽ у гайда — цена, по которой он никогда не продавался. Риск
   по ФАС озвучен владельцу, решение оставить принято сознательно. Видно на
   сайте, в боте и на обложке поста.
